FAVELLA DEVELOPMENT

A GitHub-native, role-driven engineering execution framework.

FD converts ideas into shippable increments using atomic work items, strict 1-to-1 handoffs, and GitHub Pages as its documentation interface. Every artifact is versioned, traceable, and built for handoff.

Rules and Quality Gates

These are enforced by CI where automated, and by process review where not yet automated.

File and Content Rules

✗
500-line limit
Every non-table logic/code file must be 500 lines or fewer. CI fails with: FAIL: [path] exceeds 500 lines
✗
ASCII only
No non-ASCII characters in code or docs unless a file is explicitly exempted in policy. CI fails with: FAIL: non-ASCII character found in [path]
✗
No ellipses
Do not use ... to omit content. No truncation. Write the full content or mark it as explicitly out of scope.
✗
No secrets in repo
Use placeholder values. No tokens, keys, or passwords in any committed file.

PR Requirements

■
WI link
PR title and/or body must reference the WI-### and include a link to the WI file in /backlog/work_items/.
■
AC mapping
PR body must state which ACs are satisfied by the change.
■
Evidence links
PR body must include links to /evidence/WI-###/ for all required evidence.
■
E2E update
If labeled "behavior-change," docs/E2E_VERIFICATION.md must be updated in the same PR. CI fails if not.
■
Rollback note
If the PR affects deployment, a rollback note must be present in the WI handoff checklist.

Release System

A release is a controlled, traceable event. No WI left behind. No undocumented rollback.

Release Readiness (All Required)

△
All WIs Accepted or Closed
No WI in scope may remain in Draft, In Review, or Rework at release time.
△
CI green on main
The exact commit to be tagged must have all CI jobs passing.
△
E2E executed
All regression matrix scenarios in scope must be run and evidence committed.
△
Rollback verified
Rollback steps from docs/RELEASE_RUNBOOK.md have been sanity-checked against the actual deploy target.
△
Known limitations documented
Any known limitations at release time are recorded in Section 5 of the runbook.

Rollback Procedure (Summary)

If a release causes a regression that cannot be hotfixed within one business day:

1. Identify last known-good tag (e.g., v0.9.0)
2. git checkout -b hotfix/rollback-to-v0.9.0
3. git revert HEAD..v0.9.0 --no-edit
4. git push origin hotfix/rollback-to-v0.9.0
5. Open PR to main; confirm CI passes
6. Merge PR
7. git tag -a vX.Y.Z-rollback -m "Rollback to v0.9.0 state"
8. git push origin vX.Y.Z-rollback
9. Verify GitHub Pages serves reverted state (5 min max)
10. Document incident in Release Execution Record
